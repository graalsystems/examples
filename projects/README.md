# Example projects

The directories at the root of this repository show **one job** each. The examples here are
**whole graal projects**: several jobs that hand data to each other through Iceberg tables, the
identity that runs them with only the rights it needs, and a workflow that chains them. Deploy one
in a single command, open it in the console, and run its workflow.

| Project | What it shows | Job types | Tables it writes |
|---|---|---|---|
| [`energy-consumption`](energy-consumption) | A daily data pipeline: ingestion, aggregation, quality checks that stop the workflow on a violation | `python` | `energy_hourly`, `energy_daily` |
| [`demand-forecast`](demand-forecast) | Machine learning: data preparation, a training notebook tracked in MLflow and validated against a baseline, a published forecast | `python`, `notebook` | `forecast_sales_history`, `forecast_predictions`, `forecast_weekly` |

Both use **synthetic** data generated by their first job (seeded, so every run gives the same
result): they need no dataset, no bucket and no network access from the runs.

## Deploy

Prerequisites: [`graalctl`](https://github.com/graalsystems/graalctl) logged in to your tenant, and
`jq`.

```sh
projects/deploy-project.sh projects/energy-consumption          # project, identity, rights, jobs, workflow
projects/deploy-project.sh projects/energy-consumption --run    # … and run the workflow, waiting for it
projects/deploy-project.sh projects/demand-forecast --dry-run   # print what would be created
```

The script creates (or finds, by name):

1. the **project** (`example-energy-consumption`, `example-demand-forecast`);
2. an **identity** `<project>-runner`, which the jobs and the workflow run as;
3. its **rights**, and nothing more: *Project Contributor* on the project, *Job Reader* on each job,
   *Catalog Contributor* on the tenant (to read and write the tables by name) and *Infrastructure
   Reader* on the infrastructure the runs go to;
4. the **jobs**, their code uploaded as libraries;
5. the **workflow**, whose tasks point at those jobs.

Granting rights needs a tenant administrator. Without that role, ask an administrator for an
identity with the rights above and pass it: `--identity <id>`. With more than one infrastructure,
name it: `GRAAL_INFRASTRUCTURE=<name or id>`.

Run the script again after changing a job: it **updates** what exists (code, options, workflow
tasks) and keeps the runs and their history. It never deletes anything.

## Layout of a project

```text
<project>/
  project.json     name, description, labels, and the jobs in creation order
  workflow.json    the workflow; "ref": "<JOB:ingest>" becomes the id of the job jobs/ingest
  jobs/<job>/      job.json + graal.env + code: the same format as the single-job examples
```

To make your own, copy a project, change `project.json`, and replace the jobs: each job directory
is an ordinary example that `../deploy.sh` can also deploy on its own.

## Tables by name

The jobs read and write Iceberg tables with the `graal` module that every Python and notebook run
receives:

```python
import graal

df = graal.read_table("energy_hourly")  # pandas
graal.write_table(daily, "energy_daily", mode="overwrite")  # created on the first call
```

No bucket, path or key appears in the code: the run carries a token valid for that run only, and
the tables live in your tenant's catalog. Open them in the console's catalog, or query them from the
SQL editor.
